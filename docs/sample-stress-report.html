关注吞吐在约 600 并发处饱和
饱和度拐点之后继续加压，QPS 不再增长而 P95 明显抬升，实测最大有效吞吐 8984 req/s。该并发量即为当前部署下的容量上限参考值。
关注尾部延迟放大，P99 是平均值的 4.1 倍
平均 34.9 ms、P95 64.0 ms、P99 142 ms。长尾通常来自连接池等待、慢查询或 GC 停顿，建议按 Top 慢请求逐条归因。
观察错误率 0.18%，共 3,800 次失败
主要错误类型为 HTTP（3,268 次）；错误集中在第 3:10–4:59（压测第 190–299 秒）；占比已低于 1%，属于可接受范围，但建议确认是否与重试/超时策略有关
观察90% 时间吞吐不低于 2561 req/s

结论与优化建议

Conclusion & Recommendations
有条件通过
本次压测达成主要目标，但存在需要跟进的性能风险。
优化建议P0 阻断上线 / P1 本次迭代 / P2 长期
P0
以 600 并发为基准做瓶颈下钻
该并发下吞吐已饱和而延迟抬升，说明存在明确的资源瓶颈。建议在同压力下采集服务端 CPU、GC、数据库慢查询与连接池等待指标，定位是应用层、中间件还是存储层先到极限。
P1
治理长尾延迟
P99/平均 = 4.1，尾部请求拖低了用户体验一致性。可从连接池预热与最大连接数、下游接口超时与重试退避、慢 SQL 与索引三方面入手，目标把 P99 压到平均值的 2 倍以内。
P1
排查长时间运行下的性能劣化
后半程响应时间上升 58.3%，需确认是否与内存增长（堆/堆外）、连接未释放或缓存失效有关。建议做 4 小时以上长稳压测并观察 RSS 与 GC 频率曲线。
P2
在贴近生产的环境复测
本次结果仅在所述施压端与目标环境下成立。单机施压、本机回环或缩容部署都会高估系统容量，正式容量结论应在生产等价拓扑、真实数据量与同规格机器上取得。
补充说明
系统在 600 并发时达到约 8,900 req/s，继续加至 900 / 1200 并发后吞吐基本停滞（增幅 < 5%），而 P95 从 60ms 抬升至 94 / 128ms，判定饱和拐点在 600 并发附近。
第 4 阶段起出现 503 突发，错误集中在 upstream connect error，指向应用侧连接池或上游依赖耗尽，建议优先扩大数据库连接池并复核 Redis 连接复用情况。

指标口径定义

Metric Definitions
指标定义
请求数成功请求数 + 失败请求数。失败包含连接错误、超时、以及状态码非 2xx 的响应。
平均响应时间全部请求耗时的算术平均，含失败请求，用于反映整体体验而非仅成功路径。
P50 / P95 / P99对逐请求耗时做线性插值分位数，表示「该比例请求不超过此值」。
RPS / QPS每秒完成请求数，按实际采样间隔 Δt 归一，非按固定 1 秒估算。
90% 分布 RPS每秒采样 RPS 的 P10，含义为「90% 的时间吞吐不低于该值」；已剔除升压段与首末不完整采样。
峰值 RPS所有采样点中的最大每秒请求数，仅反映瞬时能力，不代表可持续承载。
TTFB首字节时间，从请求发出到收到响应首字节的耗时，可区分网络/排队与服务端处理。
APDEX(满意请求数 + 容忍请求数 / 2) / 总请求数，容忍阈值 T = 4 × 平均响应时间。
错误率失败请求数 / 总请求数。SLA 判定与红黄绿结论均以此口径为准。
总流量发送字节 + 接收字节；趋势图中的带宽按每秒采样折算。
稳态 RPS该阶段剔除前 20%（升压）与后 10%（切换抖动）后采样 RPS 的中位数。
扩展效率吞吐增幅百分比 ÷ 并发增幅百分比；100% 表示线性扩展，明显低于 100% 说明已接近瓶颈。
报告中所有结论均可由上述口径复算。若与其他工具（JMeter / wrk / k6）对比，请先确认分位数插值方式、失败请求是否计入平均响应时间、以及升压段是否剔除，三项口径不一致会带来 10%~30% 的数值差异。

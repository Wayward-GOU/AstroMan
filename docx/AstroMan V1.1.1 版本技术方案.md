## 一、版本背景

### 1.1 本轮压测报告结论

| 阶段 | 并发 | 平均 QPS | 平均 RT | P95 | 错误 |
|---|---:|---:|---:|---:|---:|
| S1 | 300 | 3867.6 | 79.2 ms | 606 ms | 0 |
| S2 | 400 | 3881.2 | 84.9 ms | 130 ms | 0 |
| S3 | 500 | 3867.0 | 99.7 ms | 157 ms | 0 |

- 施压端：Windows 10、8 核、32 GB；压测期峰值 CPU 0.6 核（8%）、内存 70 MB。
- 300 并发已约 3868 QPS，400/500 只有约 0.3% 波动，RT 从 79 ms 升到 100 ms：**目标侧容量饱和，不是 AstroMan 客户端瓶颈**。
- 多窗口的价值是"多任务并行/多计划管理"，不是"突破单机 QPS"。

### 1.2 本版本要解决的三类问题

1. **压测可用性**：多任务/多窗口并行、全局计划中心、环境变量稳定解析。
2. **结果可信与可读**：报告全路径展示、长稳与 SLA 风险规则、基线与模板。
3. **体验修复**：记事本卡片长文本溢出、详情抽屉宽度。

  - 关闭压测窗口不中断任务：任务归注册表，窗口只是视图；重新打开同一 `jobId` 要能恢复进度（`stress_jobs()` + 路由 `jobId`），不重跑、不重复上报。

  - 崩溃恢复：运行期不写库，重启后任务不恢复，只保留已生成报告；`recover_interrupted_runs` 的口径维持不变。
  - 任务结束（完成/取消/失败）后窗口保留并展示结果；再次启动生成新 `jobId`，不复用旧 ID。

#### 1.3 并行限制与结果有效性 `P1`

- **1.3.1 并行上限（已确认）** `已完成`
  - `max_jobs` 默认 3；所有任务并发之和默认 ≤ 1000，设置可改，硬上限 2000，超出拒绝并提示。
  - 口径区分：单任务并发上限仍是 `MAX_CONCURRENT = 5000`（前后端一致，`stress.rs:23`、`StressTest.vue:321`），保持不变；1000 / 2000 是新增的「跨任务并发之和」校验层，两者不冲突。
  - 已完成本机能力检测时，并发总和超过检测饱和并发的 80% 追加警告，不硬拦。
  - 定位：该上限用于防误操作与保证报告可解释（同机 1000 并发对 8 核客户端远未到瓶颈），不是性能保护，因此不设更低。
  - 校验位置：在 `prepare_stress` 内读注册表求和并加锁判定，前端只做预校验；否则多窗口可能同时通过校验后一起启动。
- **1.3.2 同目标保护（已确认）** `已完成`
  - 对 `method + scheme + host + port + path` 归一化：完全相同默认禁止，可“忽略并继续”；同一 host 不同 path 仅警告。
  - query 不纳入判定：query 不同往往仍是同一接口同一资源，压力照样叠加。
  - 忽略必须留痕：报告 `config_json` 写 `overlap: { ignored: true, with: [jobId] }`，并在计划页与报告页标注“多任务叠加压测，不可作为单实例容量结论”。
- **1.3.3 批次标记** `已完成`

#### 1.7 本机施压能力检测 `P1`

- **1.7.1 回环检测服务** `已完成`
  - 在 AstroMan 进程内监听 `127.0.0.1:0`（随机端口）的临时 HTTP 服务，固定返回 2 字节响应并支持 keep-alive。
  - 服务只存在于检测期间，不写数据库、不生成报告。
  - 依赖缺口：`Cargo.toml` 目前没有 hyper/axum（hudsucker 间接引入的 hyper 不能直接使用）。二选一：加 `hyper-util`（`http-body-util` 已在依赖树），或手写 `TcpListener` 解析固定响应（只需 2 字节 + keep-alive，量很小）。
  - CPU/内存采样复用 `stress.rs:758-789` 已有的 sysinfo 进程采样器，不另写一套；检测期间同样每秒采样，口径与压测页一致。
- **1.7.2 阶梯探测与判定（标准档，已确认）** `已完成`
  - 档位 16 / 32 / 64 / 128 / 256 / 512 / 1024 并发，每档 3s，首 1s 预热不计入；总时长约 25s。
  - 每档记录 QPS、平均/P95 RT、错误率、CPU、内存。
  - CPU 口径为 AstroMan 进程 CPU 占整机核数比例（与压测页一致，`stress.rs:789`），不是整机 CPU；整机 CPU 只作日志参考，不参与 85% 判定。
  - 终止条件（命中任一）：QPS 增幅连续两档 < 5%；CPU ≥ 85% 连续两次采样；错误率 ≥ 1%；达到 1024 并发；或达到 60s 保护上限。
  - 输出：`maxQps`、`saturationConcurrent`、`cpuPeak`、`memPeak`、`cores`、`os`、`probedAt`、`reachedLimit`、逐档 `samples`。
  - 未触顶（1024 并发下 QPS 仍在增长且 CPU < 85%）时 `reachedLimit=false`，展示为“≥ X QPS”，并提示可提高到 2048 并发复测，不能当作极限值。

## 五、风险与取舍

| 风险 | 处理 |
|---|---|
| 同目标多窗口把叠加压力误读为单实例容量 | 默认同目标互斥；忽略时在报告与计划页标注 |
| 多任务同时写 SQLite 造成锁等待 | 运行期不写库；结束后单事务写报告；保留 WAL / busy_timeout |
| 多窗口窗口状态互相覆盖 | `stress-*` 加入 window-state denylist |
| 计划导出泄漏密钥 | 默认剔除 auth、secret 变量与解析后地址；包含敏感信息需二次确认 |
| 老库重建计划表失败或丢数据 | 迁移前备份；重建在单事务内完成，失败回滚保留旧库；版本号只升一次 |
| 旧报告无法还原真实 URL | 新报告双存模板与解析地址；旧报告明确提示，不伪造 |
| 4h 长稳与目标同机争抢资源 | 长稳模板提示使用独立施压机；报告中标注同机风险 |
| 长时压测内存增长 | 依赖已有采样降频；验证后再决定是否提高任务上限 |
| 回环检测值高于真实网络下的施压能力 | 报告标注"回环理想网络"口径；检测值只用于判断客户端是否有余量，不当作目标容量 |

## 八、分布式压测（V1.2 立项）

### 8.1 价值边界

多机施压**不会提高目标侧 QPS**。当前 300/400/500 并发都在 3868 左右、施压端 CPU 仅 0.6 核，瓶颈在目标侧，多机只能把"目标已饱和"验证得更硬。本功能的价值是：

- 单机客户端确实打不满目标时，确认不是自己拖后腿；
- 从多个网络位置观测延迟，区分链路 RTT 与服务端耗时；
- 长稳时把压力分散到多台机器，避免单机资源吃紧影响采样。

因此定位为"能力补齐"，不承诺"多机就能压出更高 QPS"。

### 8.2 架构（一期）

- **主从模型**：主节点负责调度、时钟对齐、采样合并与出报告，同时作为施压节点参与压测。
- **反向连接**：由从节点主动连接主节点，主节点不主动连从节点，避开 Windows 入站防火墙与 NAT。
- **传输**：WebSocket + JSON，主节点监听可配置端口（默认 17801），仅接受内网地址。
- **配对**：主节点展示 6 位配对码（5 分钟有效、单次使用），从节点提交后换取会话令牌；后续消息一律带令牌。
- **消息**：`hello` / `prepare` / `start{ atMs }` / `sample{ ... }` / `done` / `abort`；心跳 2s，连续 3 次丢失判定失联。

### 8.3 五个关键问题与处理

| 问题 | 处理 |
|---|---|
| 发现与配对 | 一期手动填 IP + 配对码；mDNS 自动发现放二期，且只作为便利入口，手动路径永久保留 |
| 时钟对齐 | 连接后做 5 次往返握手，取 RTT 最小样本计算偏移，采样按主节点时间轴归集；偏移误差 > 200ms 的采样丢弃并计入 `droppedSamples` |
| 目标可达性预检 | 启动前每个从节点对目标执行一次 DNS / TCP / TLS / 状态码检查，任一节点失败即拒绝启动并指明节点与错误 |
| 百分位合并 | 不对各节点的 P95 取平均：直接合并逐毫秒直方图桶后重算；平均值按请求数加权，QPS 相加，错误率按总请求数合并 |
| 节点故障 | 失联节点标记 `lost`，其余继续跑完；报告标注"结果不完整（N/M 节点）"，该节点数据只统计到失联时刻，不做并发重分配 |

### 8.4 数据模型

- `cluster_jobs`：`id`、`created_at`、`status`、`master_node`、`config_json`、`start_at_ms`、`pair_code_expires_at`。
- `cluster_workers`：`job_id`、`node_name`、`addr`、`weight`、`concurrent`、`status`、`qps`、`cpu`、`mem`、`joined_at`、`dropped_samples`。
- 合并结果写入既有 `test_reports`，报告分析、导出、HTML/Excel 全部复用，不新增第二套报告结构；`config_json` 内记录参与节点清单与权重。

### 8.5 现有代码改造点

- 把 [stress.rs](file:///d:/Software/ProjectFiles/AstroMan/src-tauri/src/commands/stress.rs) 的 worker 循环抽成"每完成一轮产出 `ReportSample` 并通过回调外送"的形式，落库与上报共用同一引擎。
- 新增 `src-tauri/src/services/cluster/`：`discovery`（二期）、`server`（主节点）、`client`（从节点）、`merge`（采样与直方图合并）。
- 环境变量只传变量名，各节点本地解析；解析失败则拒绝加入并列出缺失变量名，密钥不出本机。
- 每台机仍遵守"同时只跑一个压测任务"；并发上限按单机并发计算，集群总并发不继承 1.3.1 的 1000 上限。

### 8.6 分期

1. **一期（V1.2 主体）**：手动 IP + 配对码、单场景同步启动、并发按权重分摊、每秒采样汇总、合并报告、失联处理。
2. **二期**：mDNS 自动发现与设备列表、复用 1.7 的能力检测上报各节点极限、权重可视化配置。
3. **三期**：计划级编排、多阶段下发、断线重连、跨网段。

### 8.7 验收标准

- 两台机 smoke（合计 16 并发）：合并 QPS 与两台独立结果之和误差 < 3%。
- 任一从节点无法访问目标：启动前被拦截，提示具体节点与原因。
- 运行中杀掉一个从节点：主节点 6s 内标记 `lost`，报告生成成功且标注不完整。
- 人为把从节点系统时间调整 5 分钟：合并后 QPS / RT 曲线无时间轴漂移。
- 从节点缺失环境变量：拒绝加入且提示变量名，主节点不携带密钥下发。

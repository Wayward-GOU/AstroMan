# AstroMan 项目优化评估报告

- 评估日期：2026-11-23
- 评估对象：AstroMan v1.1.3（Vue 3 + Tauri 2 + Rust）
- 评估范围：前端页面与导出链路、Rust 命令层与数据层、构建与 CI、UI 规范、安全配置
- 评估方式：静态代码审查 + 现有质量门禁实跑 + 构建产物分析
- 说明：本报告的性能结论来自代码路径与数据规模推算，未在真实长压测数据集上做运行时采样；涉及吞吐的改动建议用仓库自带基准复核。

## 0. 结论摘要

项目整体工程化水平较高：路由懒加载、CI 门禁（单测 / 类型检查 / clippy / 审计 / 覆盖率 / 体积 / 安全断言）、主题令牌与对比度检查、错误兜底都已落地。当前最值得投入的方向不是"补功能"，而是**控制报告数据在列表与导出链路中的放大效应**，以及**修正几处文案与工具契约不一致**。

## 2. 性能优化

### P-01（高）报告列表解析完整 `config_json`

**现状与证据**

`report_list` 为了得到 `isCluster` 与 `peakQps`，会把 `config_json` 整列取出来，并且**每行解析两次**：

- SQL 与解析：[report.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/commands/report.rs#L261-L273)
- `is_cluster_config` 与 `peak_qps_config` 各自 `serde_json::from_str`：[report.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/commands/report.rs#L71-L97)

而 `config_json` 里包含两类大对象：

1. `cluster.nodeSeries`：每节点最多 1800 个采样点（[merge.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/services/cluster/merge.rs#L813-L856)）；
2. `pools[].perItem`：每个池最多 2000 条条目明细（[stress.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/commands/stress.rs#L694-L708)）。

前端有 4 处直接拉 200 份报告：`StressReportList`、`Plans`、`StressTest`（基线选择）、AI 工具。每次进入这些页面都会重复上述解析。

**影响**

- 10 节点 × 1800 点 ≈ 1.8 万个对象/report，200 份报告可达数十万对象解析；
- 列表页只需要 29 个汇总字段，却承担了报告详情的反序列化成本；
- 报告越多、节点越多、池越大，列表越慢，且占用瞬时内存。

**建议**

1. 在 `test_reports` 增加两列：`is_cluster INTEGER DEFAULT 0`、`peak_qps REAL DEFAULT 0`，写入报告时直接落列（单机在 [stress.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/commands/stress.rs#L3459-L3460)，集群在 [merge.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/services/cluster/merge.rs#L357-L358) 已算出这两个值）。
2. `report_list` 只查汇总列，不再 `SELECT config_json`；旧数据用一次性迁移 `json_extract` 回填。
3. 若暂不想改表，至少新增 `report_list_brief`，禁止列表接口返回 `config_json`。

**验收**

- `report_list(200)` 不再读取 `config_json`（可用 SQL 日志或代码审查确认）；
- 报告列表首屏耗时与报告数量、节点数、池条目数解耦；
- 列表仍能正确显示"集群"标记与峰值 QPS。

### P-02（高）Rust release 使用 `opt-level = "z"`

**现状与证据**

[Cargo.toml](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/Cargo.toml#L98-L103)：

```toml
[profile.release]
panic = "abort"
codegen-units = 1
lto = true
opt-level = "z"
strip = true
```

`opt-level = "z"` 以最小体积为目标，会牺牲循环向量化与内联，对 HTTP 压测引擎这类 CPU/网络热路径不友好。

**影响**

这是一个以性能为核心卖点的工具，安装包体积通常不是第一优先级；用 `z` 换取少量体积，可能让高并发下的客户端自身成为瓶颈，并影响 QPS/延迟统计的可信度。

**建议**

- 改为 `opt-level = 3`（或保守用 `2` / `"s"`），保留 `lto`、`codegen-units = 1`、`strip`；
- 用仓库已有的 `--features bench --example baseline` 与 `perf_node_series_24h_16_nodes`（[merge.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/services/cluster/merge.rs#L1328-L1378)）对比修改前后的吞吐与合并耗时；
- 对比安装包体积变化，若增长不可接受，再考虑只对非热路径拆分 profile。

**验收**

- 基准吞吐不低于修改前，合并/序列化耗时下降或持平；
- 安装包体积变化有记录并可解释。

### P-03（高）导出链路的 IPC 与过度取数

**现状与证据**

1. 前端生成 HTML/Excel 后，用 `Array.from(bytes)` 变成 `number[]`，经 IPC 传给后端写盘：
   - 调用侧：[ReportDetail.vue](file:///Applications/my-system/ProjectFile/AstroMan/src/views/ReportDetail.vue#L900-L916)
   - 命令签名 `data: Vec<u8>`：[report.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/commands/report.rs#L508-L512)
2. 导出前固定拉 50000 条请求明细（含请求体/响应体）：
   - [ReportDetail.vue](file:///Applications/my-system/ProjectFile/AstroMan/src/views/ReportDetail.vue#L889)
3. 但 HTML 报告实际只用到：首条请求 URL、Top 10 慢请求、样本条数（[reportExport.ts](file:///Applications/my-system/ProjectFile/AstroMan/src/utils/reportExport.ts) `resolvedTargetUrl` / `slowRows` / `secC`）。

**影响**

- `number[]` 的 JSON 序列化体积通常是原始字节的 4~5 倍，几十 MB 的 Excel 会放大成上百 MB 字符串，`Array.from` 本身也要分配同长度数组；
- HTML 导出为一个"前十名"列表加载 5 万条明细，属于明显的过度取数；
- 大报告导出可能出现主线程长时间阻塞、内存峰值陡增。

**建议**

1. **Excel 改为后端生成**：仓库已依赖 `rust_xlsxwriter`（[Cargo.toml](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/Cargo.toml#L81)），池模板已在使用。报告 Excel 可在 Rust 侧直接流式写盘，避免 5 万条明细过 IPC。
2. **HTML 只取必要数据**：优先使用 `detail.slowRequests`；无快照时最多取前 200 条，样本总数用 `report.totalRequests`，不要用 `requests.length`。
3. 若保留前端生成 HTML，评估 Tauri 原始字节通道替代 `Array.from(number[])`，或先写临时文件再原子替换（与 CSV 导出的思路一致）。

**验收**

- 导出 5 万条明细的报告时，前端内存峰值显著下降；
- HTML 导出请求明细的拉取量从 50000 降到常量级；
- 导出的 Excel 内容与当前保持一致（列、行数、分页无缺失）。

### P-04（高）报告详情全量采样：全量 DOM + 深响应式

**现状与证据**

- `detail` 使用 `ref<ReportDetail>`（[ReportDetail.vue](file:///Applications/my-system/ProjectFile/AstroMan/src/views/ReportDetail.vue#L39)），`samples` 最多可达 28800 条（8 小时 × 1 秒），全部被深响应式代理。
- 每秒明细表直接 `v-for="s in samples"`（[ReportDetail.vue](file:///Applications/my-system/ProjectFile/AstroMan/src/views/ReportDetail.vue#L1569)），虽然有 `max-height: 360px`（[ReportDetail.vue](file:///Applications/my-system/ProjectFile/AstroMan/src/views/ReportDetail.vue#L2858-L2860)），但**所有行都在 DOM 中**。
- 请求明细已经分页（每页 50），说明分页模式已在同页存在。

**影响**

- 长压测报告打开时创建数万个响应式对象与表格行，首屏与滚动都会卡顿；
- 图表 computed 还会对 `samples` 生成多份等长数组（QPS/并发/平均/P50/P95/P99/错误率），进一步放大内存。

**建议**

1. `samples` 表格改为分页（建议 200/页）或复用抓包页的窗口化方案（`listWindow`）。
2. 详情数据改为 `shallowRef`，图表所需数组在加载后一次性计算并 `markRaw`，避免对 2.8 万个采样对象做深层代理。
3. 若后端愿意配合，新增"降采样后的图表序列"接口（如最多 2000 点），详情页只取聚合 + 降采样序列，表格按需分页取原始采样。

**验收**

- 8 小时报告（28800 采样）打开时间与内存明显下降；
- 表格滚动帧率稳定，分页切换无整页重渲染；
- 图表与指标口径不变。

### P-05（中）antd 全量注册

**现状与证据**

- `main.ts` 中 `app.use(Antd)` 全量注册（[main.ts](file:///Applications/my-system/ProjectFile/AstroMan/src/main.ts#L69-L71)）；

- 调整后不要再用抬高告警阈值掩盖问题，保留 500 KB 级告警作为依赖增长预警。

**验收**

- `antd` 分包体积明显下降，首屏 JS 解析时间下降；
- 所有页面组件样式与行为无回归（可用现有 Playwright 冒烟 + 手工抽查）。

## 3. 功能与正确性问题

### B-01（中）AI 工具 `report_export` 描述与实际不符

**现状与证据**

- 工具描述："把压测报告导出为 HTML（会写入用户给出的路径）"（[aiTools.ts](file:///Applications/my-system/ProjectFile/AstroMan/src/utils/aiTools.ts#L4661-L4669)）；
- 实际调用 `reportExport` → 后端 `report_export` 写入的是 `astroman.report` **JSON 归档**（[report.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/commands/report.rs#L390-L418)），前端 API 也只有 `report_export` 这一条后端命令（[api/index.ts](file:///Applications/my-system/ProjectFile/AstroMan/src/api/index.ts#L668-L672)）。

**影响**

- 用户说"导出 HTML"，航仔会生成 `.html` 路径，但文件内容是 JSON，打开后不符合预期；
- 与报告页"HTML 报告"导出能力不一致。

**建议**

- 二选一：
  1. 改描述与返回文案为"导出 JSON 归档"，并明确建议 `.json` 扩展名；
  2. 新增后端或前端 HTML 导出工具（前端 `buildReportHtml` + `reportWriteFile`），真正产出 HTML。
- 同时在工具参数说明里约束扩展名，避免路径与内容不一致。

### B-02（中）集群报告"压测模式"文案错误

**现状与证据**

- 集群报告写入时把 `mode` 覆盖为 `"cluster"`（[merge.rs](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/src/services/cluster/merge.rs#L393-L395)）；
- 报告页头部：`config.mode === 'stages' ? '阶梯加压' : '固定并发'`（[ReportDetail.vue](file:///Applications/my-system/ProjectFile/AstroMan/src/views/ReportDetail.vue#L805)），集群阶梯计划会被显示为"固定并发"；
- 报告页配置快照同样只判断 `stages`（[ReportDetail.vue](file:///Applications/my-system/ProjectFile/AstroMan/src/views/ReportDetail.vue#L1643)）；
- Excel 导出直接回退原始值，会显示英文 `cluster`（[reportExport.ts](file:///Applications/my-system/ProjectFile/AstroMan/src/utils/reportExport.ts#L2445)）。

**建议**

- 统一模式文案函数：`cluster` → "分布式压测（阶梯）/（固定）"，依据 `stages.length` 区分；
- 页面、HTML、Excel 共用同一映射，避免三处口径漂移；
- 增加一条单测覆盖集群模式文案。

### B-03（中）`security:check` 在 Node < 20.11 崩溃

**现状与证据**

实跑 `npm run security:check`（Node v18.20.8）报错：

```
TypeError [ERR_INVALID_ARG_TYPE]: The "paths[0]" argument must be of type string. Received undefined
    at file:///.../scripts/check-release-security.mjs:13:14
```

原因：脚本使用 `import.meta.dirname`（[check-release-security.mjs](file:///Applications/my-system/ProjectFile/AstroMan/scripts/check-release-security.mjs#L13)），该属性 Node 20.11 才引入；[gen-sbom.mjs](file:///Applications/my-system/ProjectFile/AstroMan/scripts/gen-sbom.mjs#L11) 同样存在。

CI 使用 Node 22，所以流水线能过；但本地/新成员按文档装 Node 20.0~20.10 会直接失败。

**建议**

- 脚本改为 `fileURLToPath(new URL('..', import.meta.url))`，兼容 Node 18+；
- `package.json` 增加 `"engines": { "node": ">=20.11" }` 并补 `.nvmrc`；
- `docs/development.md` 把"Node 20.x"改为"20.11+"（当前写 20.x/22.x）。

---

### B-04（低）缺少 Node 版本约束的连带影响

无 `engines`、无 `.nvmrc` 时，`npm ci` 不会提示版本不匹配，问题会在跑脚本时才暴露。建议与 B-03 一并修复。

## 5. 安全

[tauri.conf.json](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/tauri.conf.json#L25) 中 `script-src 'self' 'unsafe-eval'`。原因是脚本能力使用 `new Function`（[scriptRunner.ts](file:///Applications/my-system/ProjectFile/AstroMan/src/utils/scriptRunner.ts#L266)），无法直接移除。

## 6. 工程质量

### Q-01 前端缺少 ESLint / Prettier（中）

仓库没有 ESLint/Prettier 配置，`package.json` 也没有 lint 脚本；CI 只跑类型检查、样式门禁与单测。建议引入：

- `eslint` + `eslint-plugin-vue` + `@typescript-eslint`；
- 规则先以 `warn` 起步，重点拦未使用变量、危险的 `v-html`、浮动 Promise、`any` 增长；
- 配合 Prettier 统一格式，减少纯排版 diff。

### Q-02 覆盖率门禁偏低（中）

- Rust：`fail-under = 25`（[tarpaulin.toml](file:///Applications/my-system/ProjectFile/AstroMan/src-tauri/tarpaulin.toml)），而文档目标为 ≥60%；
- 前端：Vitest 未配置覆盖率，也没有阈值。

建议分阶段抬升：Rust 先 25→35→45，前端先统计再设阈值；优先覆盖报告聚合、池切片、变量合并、导出等核心纯函数。

### Q-03 巨型单文件组件（中）

`RequestEditor.vue` 6354 行、`AiAssistant.vue` 6144 行，单文件同时承载模板、状态、请求编排与样式。建议按功能拆分为 composable + 子组件（编辑器、脚本面板、Mock 面板、AI 会话列表等），降低回归风险与 review 成本。

### Q-04 测试临时目录残留（低）

本地 `src-tauri/target/test-tmp` 已累积 675 MB / 1599 个目录（已被 `.gitignore` 忽略）。建议在测试 util 中增加清理守卫（Drop 或按测试结束时间清理），避免长跑 CI/本地磁盘膨胀。

### Q-05 CI 已具备的能力（保持）

- 生产依赖审计、版本一致性、单测、样式门禁、构建、安全断言、SBOM、产物体积门禁；
- Playwright 冒烟 6 条；
- Rust fmt / clippy `-D warnings` / cargo audit / test / bench 示例编译 / 覆盖率；
- 这套门禁质量较高，建议只补前端 lint 与覆盖率，不要重复造轮子。
